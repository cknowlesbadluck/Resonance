# Resonance Audit — 14 September 2026

Audited against `main` @ `b331906`. Every claim below was verified by running the code, not by reading docs.

**Baseline health:** typecheck clean · 90 tests pass, 1 skipped · production build clean · 16 migrations · RLS present.
The build being green is precisely why the real defects survived: they are contract defects, not compile errors.

---

## 1. Headline finding — the capability plane was advertised but not executable

`GET /api/nexus/capabilities` returned 17 capabilities. Only 3 could ever run.

The other 14 — the entire catalog (`tool.github`, `skill.ios-swiftui`, `integration.supabase`, …) — failed at compose time, **every one of them**, for three independent reasons stacked on top of each other:

| Wall | Cause |
|---|---|
| Registry | `composeIntent` reads only `nexusRegistry`; catalog capabilities were never registered into it. Result: `No compatible capability for <key>` — 14/14. |
| Policy | Catalog capabilities declare grants like `repo.read`, `database.write`, `model.invoke`. `DefaultNexusPolicy` ranks only `read…admin` and **hard-denies anything else**. Result: `unsupported permission` — 14/14. |
| Adapter | Catalog `providerId` is a display name (`"GitHub"`, `"Build iOS Apps"`). Adapter lookup matches on `adapterId`/`providerId`, so nothing bound. |

Measured before the fix:

```
advertised=14  uncomposable=14  policy-denied=14
```

This is the actual state of "P2 capability-plane convergence": the **read** path converged, the **execute** path never did. Discovery and execution were two disconnected planes that happened to share a type name. The control plane was making promises the runtime could not keep — which is the one failure mode a product whose thesis is *"integration without domination"* cannot afford.

### Root cause: two permission vocabularies that never met

`lib/domain.ts` / `src/domain/types.ts` define policy **levels** (`read | analyze | modify | execute | commit | create_pr | merge | deploy | admin`). `lib/capabilities.ts` declares **grants** (`repo.read`, `pr.write`, `agent.execute`). Nothing translated between them, and the policy failed closed on everything it didn't recognise. The security posture was technically correct and functionally total.

### Second-order finding: risk was fabricated

`capability-bridge.ts` stamped `risk: "medium"` on every catalog capability via a `DEFAULT_RISK` constant. Policy is documented as unbypassable — but it was evaluating **invented inputs**. `tool.github` (which declares `repo.write` + `pr.write`) and `tool.figma` (`design.read`) carried identical risk.

## 3. Server correctness and security

| ID | Sev | Finding |
|---|---|---|
| **SRV-1** | High | `GET /api/nexus/capabilities` **wrote to Supabase on every read** — `saveCapability` per capability, plus a fresh Supabase client per request. Under `RESONANCE_AUTH_MODE=optional` this is an unauthenticated write path. Persistence belongs to registration, not discovery. |
| **SRV-2** | Med | `memoryExecutions` / `memoryEvidence` were module-level arrays with **no cap** — unbounded growth on a long-lived host; per-instance, non-deterministic results on a serverless one. |
| **SRV-3** | Med | Rate limiting is a `count(*)` followed by an `insert` — a TOCTOU window. Concurrent bursts can exceed `RATE_LIMIT_MAX_REQUESTS`. The claim-token fencing for idempotency is genuinely well done; the rate limiter is not held to the same standard. |
| **SRV-4** | Med | `GET /executions` silently falls back to per-instance memory when `projectId` is absent, returning a different answer per lambda instance with `source: "memory"` as the only signal. |
| **SRV-5** | Low | Composition errors were opaque. `No compatible capability for X` was indistinguishable from "X does not exist", "X is planned", and "X exists but you lack the grant". |
| **SRV-6** | Low | 4 npm advisories (3 moderate, 1 high), all `postcss` transitively via `next`. Fix requires `next@16` — a major upgrade, not a hotfix. |

## 4. iOS client (`ios/`)

The client is well-structured — actor-isolated, `Sendable`-clean, forward-compatible enum decoding, Keychain-only token storage. The defects are contract defects.

| ID | Sev | Finding |
|---|---|---|
| **IOS-1** | **High** | **A failed execution lost its evidence.** The server returns `422` with a complete `{intent, plan, execution, evidence}` envelope when an execution fails. `URLSessionNexusTransport` threw on every non-2xx and discarded the body. The client could report *that* it failed, never *why*, and never surfaced the audit evidence the Nexus went to the trouble of producing. |
| **IOS-2** | **High** | **The mandated 400/401/409/422 mapping did not exist.** Everything collapsed into `httpStatus(Int, String?)`. Four statuses that demand four different user responses (fix the request / re-authenticate / new idempotency key / show the failure) were indistinguishable. |
| **IOS-3** | **High** | **`projectId` defaulted to `"demo"`** in both `NexusClientFactory` and `NexusIntentRequest`. The server requires a UUID and returns 400. The default client configuration was guaranteed to fail against any deployment with auth or persistence enabled. |
| **IOS-4** | Med | Error rendering was duplicated across four surfaces (three App Intents + `ResonanceApp`) and had already drifted — only `ExecuteNexusPlanIntent` handled 429. |
| **IOS-5** | Med | **`App/` is not in `Package.swift`.** CI's `swift test --package-path ios` compiles `ResonanceCore` only. Every App Intent and the SwiftUI app are **never built in CI**. |
| **IOS-6** | Low | `?projectId=` is interpolated into the path without percent-encoding. |
| **IOS-7** | Low | No `URLSessionConfiguration` timeout; no cancellation propagation. |

## 5. What I implemented in this pass

All changes are additive and reversible. No schema migration, no destructive operation, no vendor lock-in — see §7 on governance.

**Capability plane convergence (the headline fix)**
- `src/nexus/grants.ts` *(new)* — one canonical translation seam between grant and level vocabularies, plus `riskForGrants`. **Fail-closed is preserved**: an uninterpretable grant still denies. Normalization widens what is *understood*, never what is *allowed*.
- `src/nexus/policy.ts` — evaluates normalized grants; also refuses any capability with no bound adapter *before* it can reach an executor.
- `src/nexus/capability-bridge.ts` — now pure core, imports nothing from `lib/` (**fixes ARCH-1**). Risk is derived from declared authority instead of the `DEFAULT_RISK` constant.
- `lib/nexus-catalog.ts` *(new)* — catalog-backed source in the outer layer. Dependency arrow now points inward.
- `src/composition/root.ts` *(new)* — explicit composition root (**fixes ARCH-2**). Registers catalog capabilities with the runtime registry and binds providers to adapters. It is the only module that knows about both layers, and it is what the HTTP layer imports.
- `NexusCapability` gains `executable` / `unexecutableReason` — separating *"the provider offers this"* (`availability`) from *"this deployment can run it"* (`executable`). **The API now tells the truth about what it can do.**
- `src/nexus/composer.ts` — distinguishes not-registered / filtered / denied / adapter-unbound, each with a specific message and a `CompositionError` code (**fixes SRV-5**).

**Server**
- Capabilities route is now a pure read (**fixes SRV-1**).
- Memory buffers hard-capped at 200 (**fixes SRV-2**).

**iOS**
- `NexusHTTP.swift` + `NexusClientError.swift` *(new)* — status-preserving transport envelope and the explicit 400/401/409/422/429 contract, with `isRetryable` and a single `userFacingMessage` (**fixes IOS-2, IOS-4**).
- `NexusClient.execute` returns the decoded envelope on 422 instead of discarding it (**fixes IOS-1**).
- `projectId` is validated client-side; the `"demo"` default is gone (**fixes IOS-3**).
- `NexusTransport` gained `getResponse`/`postResponse` with default implementations, so every existing conformance still compiles.

**A regression I caught and fixed mid-flight:** the first cut of `grants.ts` used object literals for its lookup tables, which resolve inherited keys — `constructor` and `toString` would have been admitted as valid grants. The repo's existing CHR-47 prototype-pollution test caught it immediately. Both tables are now `Map`s. That test earned its keep.

**Verification:** typecheck clean · **106 tests pass** (was 90), 1 skipped · production build clean.
`src/composition/root.test.ts` is the standing guard: it asserts no advertised capability can ever again fail with an opaque lookup miss.

## 6. Second pass — hardening (same branch)

**Server**
- **SRV-3 fixed.** The rate limiter counted before inserting, so N concurrent requests could each read an under-limit count and all proceed. It now claims first and counts second: every caller has inserted its own row before counting, so concurrent callers see each other and exactly the overflow is rejected. A throttled attempt deletes its own claim so the idempotency key is not burned. Replays skip the check entirely — returning a stored response costs nothing.
- **SRV-4 fixed.** `GET /executions` returned per-instance memory when `projectId` was absent despite durable persistence being configured, so the answer varied by lambda instance with `source: "memory"` as the only signal. It now returns `400` asking for the scope.
- **Consistency bug found and fixed.** `POST /executions/[id]/resume` still composed through `src/nexus/runtime` rather than the composition root, so an approval-gated *catalog* capability could be approved and then fail to resume. All three compose paths now go through the same root.
- **ARCH-3 partly closed.** `lib/domain.ts` had zero importers and had already drifted from `src/domain/types.ts`. Deleted.

**Architecture is now enforced, not asserted** — `src/composition/architecture.test.ts`:
- `src/nexus` may not import from `lib/`, `app/`, or `src/composition`.
- Exactly one module (`src/composition/root.ts`) may bridge `src/nexus` and `lib/`.
- No route may compose intents without going through the composition root.
- Every execution-creating route must enforce idempotency by header **or** by path-scoped compare-and-swap.

That last rule caught a real gap on its first run: the resume route creates executions and sends no `Idempotency-Key`. On inspection it is genuinely safe — the path `id` *is* the key and the conditional `status=waiting → accepted` update is a compare-and-swap, so a second concurrent resume matches zero rows and gets a `409`. Rather than weaken the rule to make the test pass, both legitimate mechanisms are now encoded explicitly, with the reasoning in the test.

**iOS**
- **IOS-6 fixed.** Query parameters are percent-encoded. Notably *not* via `URLComponents.queryItems`: that setter treats `&`, `=` and `+` as legal query characters and leaves them unescaped inside a value, so a value containing `&` silently becomes a second parameter. The allowed set is narrowed and the query assembled explicitly.
- **IOS-7 fixed.** 30s request timeout, matching the control plane's execution ceiling. `URLSession.shared` defaults to 60s — long enough for a stalled request to look like a hung UI.

**Branch hygiene (P5-13) — already resolved.** The ~20 duplicate `event-lifecycle*` branches are gone. `origin` has 11 branches; 9 are stale feature/fix branches safe to prune after review.

**Verification:** typecheck clean · **112 tests pass** (was 90 at audit start), 1 skipped · production build clean.

## 8. Governance note

Per the Two-Key Reformation Rule, two changes in this pass touch **core domain semantics** and should be treated as requiring a second explicit approval before they are considered settled:

- **Adding `executable` / `unexecutableReason` to `NexusCapability`** — extends one of the nine first-class concepts.
- **Grant normalization in `DefaultNexusPolicy`** — changes what the policy plane accepts as a permission.

Both were kept deliberately additive and reversible for exactly this reason: no migration was applied, no existing field changed meaning, and both can be reverted with a single commit. I did **not** apply any Supabase migration or any irreversible operation in this pass.

The Quicksilver litmus test was applied to every new abstraction. `grants.ts`, `executable`, and the composition root all make complete sense with no iOS client at all — they are properties of the capability contract, not of any consumer.
