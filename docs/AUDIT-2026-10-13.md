## Executive Verdict
Resonance has the right skeleton: a provider-neutral Nexus with intents → composition → executions → resume, typed adapters, an idempotency layer, and a Swift `ResonanceCore` client library. It isn't yet the finished product (5/10). Production is blocked on one owner secret. **There is no runnable iOS app yet**: `ios/Package.swift` builds only the `ResonanceCore` library and tests, and no Xcode app target compiles `ios/App`. The library can list capabilities, compose and execute, but it **can't approve or resume**. The capability model is one server shape bridged to `NexusCapability` (`capability-bridge.ts`), but it's hand-mirrored in TS and Swift rather than generated. Hardening (fail-closed auth #174, rate limits #175, bounded idempotency #186) sits unreviewed. The biggest lever is human review throughput, not more code.

## Key Features
- Provider-neutral adapters (github, linear, mcp, http) behind capability gates; adapter contract tests (#182).
- Composer with ranked candidates; failover (#188) open.
- Execution with idempotency keys and resumable executions (`/api/nexus/executions/[id]/resume`).
- Host-neutral deploy contract: `/api/ready` reports env NAMES only (now pinned by a privacy-floor test, #198).
- Swift `ResonanceCore` library (NexusClient, Keychain token store) for the future iOS peer.

## Structural Weaknesses
1. **No iOS app, and iOS can't approve.** There's no Xcode app target, so `ios/App` is never compiled. `NexusClient` has no resume/approve call, so a gated execution can only be finished from the web.
2. **Hand-mirrored capability types.** The client-only module is already retired (#156), but the TS and Swift `NexusCapability` types are maintained by hand and can drift. #158 (conflicting) is leftover cleanup.
3. **Idempotency is per-instance memory** in memory mode and unbounded (#186). On serverless this is best-effort, not a guarantee; durable idempotency needs the Supabase path working (owner key).
4. Auth mode defaults aren't fail-closed until #174 lands; prod detection relies on `NODE_ENV`/stage (#185).
5. RLS posture is unverified against live (#195/#196). The SECURITY DEFINER `search_path` migration (#173) is owner-applied only.
6. `authMode` in `/api/ready` echoes the raw `RESONANCE_AUTH_MODE` value. It's non-secret, but it should be clamped to an enum.
7. Review bottleneck: main requires one review, and nothing has merged since the stack on #161.

## Recommended New Implementations
1. Create the Xcode app target for `ios/App`. Add `NexusClient.resume(executionId:decision:)`, using the existing path-scoped resume semantics, plus a Swift contract test against the same fixtures the web route tests use.
2. Generate `NexusCapability` from one server schema (JSON Schema → TS + Swift) so the two clients can't drift.
3. Keep the current mechanisms: intents are compose-only, and resume uses a CAS status claim. Make `Idempotency-Key` mandatory on execution-creating calls, backed by a durable store once Supabase is ready, with a test that a replay returns the same execution id.
4. Clamp `authMode` to `required|optional|auto` in the readiness body.
5. A review-train doc: merge order #161 → #174/#185 → #186/#175 → #172/#177/#181 → tests (#176/#180/#184) so one reviewer pass clears the stack.
